# AI Agent 2기 1주차 과제 — gkmin230

## 1. 1주차 수업 정리 — LLM 구성과 출력 제어

이번 수업에서는 LLM의 동작 원리와 API를 이용해 응답을 제어하는 방법을 배웠다.

### 1.1 LLM 동작 원리

LLM은 입력된 문장을 토큰 단위로 나누고, 학습된 패턴과 문맥을 바탕으로 다음 토큰을 예측해 응답을 생성한다. 이를 반복하는 방식을 Autoregressive 생성이라고 한다. API 호출은 이미 학습된 모델을 사용하는 추론 과정이다.

### 1.2 토큰과 Context Window

토큰은 LLM이 텍스트를 처리하는 기본 단위이며, Context Window는 한 번에 참고할 수 있는 문맥의 범위이다. 토큰 사용량은 비용과 처리 시간에 영향을 주고, 출력 한도에 도달하면 응답이 중간에 끊길 수 있다.

### 1.3 API 요청과 생성 설정

API 호출 시 모델, 지시문, 입력 데이터, 출력 형식, 생성 설정값 등을 지정한다.

Temperature는 응답의 다양성에 영향을 주고, Top-p는 토큰 선택 시 고려하는 후보 범위를 조절한다. 출력 토큰 한도는 생성 가능한 응답의 최대 크기를 제한한다.

실험에서는 하나의 조건만 변경하고 나머지는 동일하게 유지해야 결과를 비교할 수 있다.

### 1.4 구조화 출력과 검증

JSON이나 Schema를 활용하면 응답을 일정한 형식으로 받을 수 있다. 하지만 형식이 올바르더라도 내용이 정확하다는 보장은 없으므로 응답 상태, 데이터 구조, 실제 판단의 정확성을 별도로 검증해야 한다.

### 1.5 느낀 점

LLM을 실제 업무에 활용하려면 단순히 답변을 생성하는 것보다 출력 형식을 제어하고 결과를 검증하는 과정이 중요하다고 느꼈다. 이번 API 실험에서도 동일한 보안 로그에 대해 프롬프트를 구체적으로 작성했을 때 응답 형식이 더 일관되게 나타나는 것을 확인했다.

## 2. 스탠퍼드 강의 정리 — LLM의 한계와 보완 방법

강의: Stanford CS230 — Agents, Prompts, and RAG

영상: [Stanford 강의 영상](https://www.youtube.com/watch?v=k1njvbBmfsw)

강의에서 다룬 LLM의 한계 중 세 가지를 선정하고, 실제 발생할 수 있는 문제와 보완 방법을 정리했다.

### 2.1 환각(Hallucination)

LLM은 사실과 다른 내용을 실제 사실처럼 자연스럽게 생성할 수 있다.

보안관제 업무에서 HTTP 로그 분석을 요청했을 때, 로그에 없는 공격 성공 여부나 피해 범위까지 단정할 수 있다. 예를 들어 GET /.env 요청에 403 응답이 있었다는 사실만으로 모든 경로에서 정보 유출이 없었다고 판단할 수는 없다.

보완 방법으로는 RAG를 활용해 관련 로그나 문서를 검색하여 근거로 제공하고, 확인된 사실과 추정을 구분하도록 요청하며, 중요한 판단을 실제 로그와 비교해 검증하는 방법이 있다.

### 2.2 최신 정보 및 전문 지식 부족(Knowledge Gaps)

LLM은 학습 데이터의 시점에 영향을 받기 때문에 최신 사건이나 기술 변화를 모두 알 수 없다. 특정 전문 분야에서 충분한 성능을 발휘하지 못할 수도 있다.

신규 CVE 분석 시 최신 패치 버전이나 영향을 받는 제품 버전을 잘못 안내하면 실제 보안 대응에 문제가 발생할 수 있다.

이를 보완하기 위해 웹 검색과 외부 API, RAG를 활용하고 제조사 보안 공지 및 NVD 같은 공식 자료를 통해 최신 정보를 검증할 수 있다.

### 2.3 컨텍스트 윈도우의 제한(Context Window)

LLM은 한 번에 처리할 수 있는 토큰 수에 제한이 있으며, 입력 가능한 문맥이 길어도 그 안에서 특정 정보를 정확하게 찾는 것은 별개의 문제다. 강의에서는 긴 문서 속 특정 정보를 찾아내는 Needle in a Haystack 문제를 소개했다.

대량의 보안 로그를 한 번에 입력하면 중요한 이벤트를 놓치거나 여러 시간대에 발생한 이벤트의 연관성을 제대로 파악하지 못할 수 있다.

이를 보완하기 위해 로그를 시간대나 이벤트 유형별로 나누는 Chunking, 중요 이벤트 요약, 관련 데이터 검색을 위한 RAG 등을 활용할 수 있다.

### 2.4 강의를 통해 이해한 점

LLM의 성능을 개선하는 방법은 단순히 더 좋은 모델을 사용하는 것만은 아니다. 프롬프트를 구체적으로 작성하거나 외부 데이터를 검색해 제공하는 방식도 실제 업무 활용도를 높일 수 있다.

특히 보안관제에서는 LLM을 분석 보조 도구로 활용하되 실제 공격 여부와 영향도는 근거를 확인해야 한다고 생각한다. 이번 API 실험에서도 프롬프트를 구체적으로 작성했을 때 응답 형식이 더 일관되게 나타나는 것을 확인했다.

## 3. 실제 API 실험

실험 주제: **프롬프트 구체성에 따른 HTTP 보안 로그 분석 결과 비교**

아래 내용은 기존 실험 README의 설계·실제 결과 비교·관찰·한계 분석을 가져와 정리한 것이다. 제출 준비 중 API를 새로 호출하지 않았고, 기존 응답을 재생성하지 않았다.

### 실행 결과와 실험 목적

동일한 가상 HTTP 로그에 대해 지시문의 구체성만 바꾸고, 공격 의심 판단·근거·추가 확인 사항의 포함 여부와 응답 구조가 달라지는지 관찰하는 실험이다.

**2026-10-31 19:49:49~19:50:15(한국 시간) 재실행: 6회 요청 모두 성공, 오류 0회.** 조건 A와 B를 각각 3회 독립 호출했으며, 모든 응답은 `completed` 상태와 비어 있지 않은 분석 텍스트를 반환했다. [results.json](results.json)에는 이 재실행의 실제 응답 6개가 들어 있다.

크레딧 충전 전 최초 시도에서는 6회 모두 HTTP 429 `credit_balance_exhausted` 오류가 발생했다. 해당 오류 기록은 `results-initial-errors.json`에 따로 보존했다. 누적 요청은 최초 실패 6회와 재실행 성공 6회를 합쳐 12회이며, 아래 비교에는 재실행 6회만 사용한다.

### 입력 데이터

```text
GET /.env HTTP/1.1
User-Agent: python-requests/2.31.0
HTTP Status: 403
```

사용자가 제공한 가상 로그 그대로 사용했다. 실제 웹 서버에 요청하거나 공격을 수행하지 않고, 문자열을 LLM API 입력으로만 전달한다.

### 변경 조건과 프롬프트

조건 A의 지시문:

```text
다음 HTTP 로그를 분석해줘.
```

조건 B의 지시문:

```text
다음 HTTP 로그를 공격 의심 여부, 판단 근거, 추가 확인 사항으로 구분해 분석해줘.
```

각 전체 프롬프트는 `지시문 + 줄바꿈 2개 + 입력 로그`이며, 실제 전송한 문자열은 `results.json`의 각 실행 항목 `prompt`와 `request.input`에 저장했다. 지시문의 구체성과 그에 따른 길이 차이만 독립변수로 둔다.

### 유지 조건, 모델과 SDK

| 항목 | 고정값 |
| --- | --- |
| 모델 | `gpt-5.4-mini-2026-03-17` (날짜가 고정된 스냅샷) |
| 공식 SDK | Python `openai==3.42.0` |
| 실제 실행 Python | 3.10.0 |
| API | Responses API, `POST https://api.openai.com/v1/responses` |
| 입력 | 위의 동일한 3줄 로그 |
| 최대 출력 토큰 | `max_output_tokens=1600` |
| 추론 설정 | `reasoning={"effort": "none"}` |
| 서버 응답 저장 | `store=False` |
| temperature | 요청에서 생략 |
| 기타 생성 설정 | `top_p`, `seed`, 구조화 출력 형식 등 생략; 동일한 서버 기본값 적용 |
| 실행 방식 | 조건별 3회, 총 6회; A1 → B1 → A2 → B2 → A3 → B3 |
| SDK 재시도 / 제한 시간 | `max_retries=0` / 요청당 90초 |
| 대화 이력 | 매 요청은 현재 프롬프트 하나만 전달; `previous_response_id`, `conversation` 생략 |

이전 응답을 다음 요청에 전달하지 않는다. 순서를 교대로 배치해 시간 경과와 조건의 결합을 줄였지만, 순서 효과를 완전히 제거한 실험은 아니다. 모델이 응답 본문에 반환하는 기본 설정은 요청에서 해당 설정을 명시했다는 뜻이 아니다.

#### 공식 문서 확인

2026-10-31 공식 OpenAI documentation을 직접 열어 확인했다.

- [GPT-5.4 mini 모델 문서](https://developers.openai.com/api/docs/models/gpt-5.4-mini): 날짜 고정 스냅샷, 텍스트 입출력, Responses API 및 `reasoning.effort=none` 지원을 확인했다.
- [Responses 생성 API 문서](https://developers.openai.com/api/reference/python/resources/responses/methods/create): `input`, `model`, `max_output_tokens`, `reasoning`, `store` 요청 필드를 확인했다.
- [공식 Python SDK 문서](https://developers.openai.com/api/reference/python): `OpenAI` 클라이언트, `responses.create`, 환경변수 기반 인증 및 `max_retries=0` 사용법을 확인했다.

재실행 6회 모두 서버가 반환한 모델명도 요청한 `gpt-5.4-mini-2026-03-17`과 일치했다. 요청에는 temperature를 포함하지 않았으며, 여섯 요청의 생성 설정과 입력 로그가 동일함을 저장된 요청에서 확인했다.

| --- | --- | --- |

| 추가 점검 또는 대응 제시 | 3/3 | 3/3 |
| 지정한 세 제목 모두 사용 | 0/3 | 3/3 |
| 응답 구성 | 로그 해석, 의미, 보안 평가, 권장 대응 등 자율 구성 | 공격 의심 여부 → 판단 근거 → 추가 확인 사항 순서 유지 |

지정한 세 제목은 `공격 의심 여부`, `판단 근거`, `추가 확인 사항`이다. 내용 포함 여부는 응답을 직접 읽어 판단했으며, A에는 해당 형식을 요구하지 않았으므로 세 제목이 없다는 사실을 실패로 간주하지 않는다.

A1은 민감한 설정 파일을 노린 접근 시도로 해석했고, A2는 자동화된 접근 시도와 중간 이상 위험도를 제시했다. A3도 정보수집/취약점 탐색 시도로 판단했다. B1과 B2는 공격 의심을 높게 보았고 B3도 공격 의심 가능성이 높다고 분류했다. 공격 의심에 대한 큰 결론은 두 조건에서 비슷했다.

B에서는 B1의 차단 주체·응답 헤더 확인, B2의 정상 모니터링 서버·보안 점검업체 여부 확인, B3의 과거 200 응답·다른 로그 확인 등 추가 확인 사항이 독립된 항목에 모였다. A도 동일 IP의 후속 요청과 실제 노출 여부를 점검하도록 제안했으므로, 구체적 지시가 있어야만 후속 점검이 나온다고 해석할 수 없다.

#### 조건 A 관찰 (4줄)

- 3회 모두 `.env` 접근을 민감정보 탐색이나 자동화된 의심 요청으로 해석했다.
- 3회 모두 로그 해석과 보안 평가, 후속 점검 또는 대응을 자율적인 제목으로 구성했다.
- 평균 983.7자였고 836~1,179자로 길이와 제목 구성에 차이가 있었다.
- A3은 유출이 막혔다고 단정하는 표현을 사용해, 403만으로 판단 가능한 범위를 넘어서는 부분이 있었다.

#### 조건 B 관찰 (4줄)

- 3회 모두 공격 의심 여부, 판단 근거, 추가 확인 사항이라는 세 제목과 순서를 따랐다.
- 3회 모두 의심 요청으로 보면서 `.env`, 자동화 가능성을 시사하는 User-Agent, 403을 근거로 설명했다.
- 평균 1,249.0자로 A보다 약 27% 길었으며 추가 확인 사항을 별도 항목에서 구체화했다.
- B2는 정상 모니터링·보안 점검 요청 가능성도 확인하도록 제안했지만, 다른 반복에도 이런 유보가 일관되게 나타난 것은 아니다.

#### 해석과 한계

이번 6개 응답에서는 구체적인 지시가 요청한 형식의 일관성과 비교 편의성을 높였다. 핵심 판단과 후속 점검은 A에도 모두 있었으므로 B의 보안 분석 정확성이 더 높다고 결론 내리지는 않는다. 응답이 길다는 사실만으로 품질 향상을 의미하지도 않는다.

User-Agent는 조작될 수 있어 실제 Python 클라이언트나 악의적 의도를 확정하지 못하고, 단일 403 로그는 파일 존재나 과거·다른 경로의 유출 여부까지 증명하지 못한다. 일부 응답은 이를 충분히 구분하지 않았다. 제공된 로그에는 출발지 IP와 시각, 응답 본문 등이 없어 실제 공격 여부를 확정할 정답 자료도 없다.

조건별 3회와 단일 로그를 사용한 탐색적 관찰이므로 일반적 성능 차이나 통계적 유의성을 주장하지 않는다. temperature를 생략했으므로 응답이 매번 동일하게 나올 것으로 기대하지 않는다. 프롬프트 길이 증가와 항목 지정의 효과를 이 실험만으로 분리할 수는 없다.

### 실제 응답과 오류 기록의 위치

- [results.json](results.json): 성공한 실제 응답 6건. `runs` 순서는 A1, B1, A2, B2, A3, B3이고, 각 항목의 `condition`과 `repeat`로 구분한다. 응답 원문은 `runs[i].output_text` 및 `runs[i].response.output[].content[].text`에 있다.
- [results-initial-errors.json](results-initial-errors.json): 충전 전 실패 6건. 각 항목의 `error.body`에 실제 서버 오류가 있고, `error.http_status`는 429, 오류 코드는 `credit_balance_exhausted`이다. 분석 응답이 없던 실행이므로 `response`와 `output_text`는 `null`이다.
- 두 JSON 모두 각 요청의 전체 프롬프트(`prompt`, `request.input`), 요청 모델, 생성 설정, 반복 번호, 시각, 상태, 성공 여부와 집계를 보존했다.

### 공개 제출본에서 제외한 식별자

요청 ID는 서비스 지원과 진단을 위한 식별자이며, 이번 과제의 결과 비교에는 필요하지 않다. 인증 비밀은 아니지만 불필요한 진단 식별자를 공개하지 않기 위해 JSON 공개본에서 `request_id`, `response.id`, `response.output[].id` 및 오류의 `error.request_id`를 제외했다. 성공 기록에서 18개, 오류 기록에서 6개를 제외했다.

이 식별자 외의 JSON 데이터는 원본과 동일하며, 실제 분석 응답과 오류 메시지는 수정하지 않았다. 식별자를 포함한 로컬 원본은 별도로 보존했다. [experiment.py](experiment.py)와 [requirements.txt](requirements.txt)는 기존 파일을 바이트 단위로 그대로 복사했다. 따라서 실행 코드에는 진단 ID를 기록하는 원래 동작이 남아 있으며, 향후 새 결과를 공개할 때에도 식별자 포함 여부를 확인해야 한다.

### 실행 방법

Python 3.10 이상과 `OPENAI_API_KEY` 환경변수를 사용한다. 아래는 재현을 위한 안내이며 제출 준비 과정에서는 실행하지 않았다.

```sh
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
```

API 키를 환경변수로 설정한 상태에서 다음을 실행한다. 키를 코드나 파일에 적지 않는다.

```sh
python experiment.py --output results-rerun.json
```

기존 결과는 덮어쓰지 않도록 보호되어 있다. 위 명령을 실행하면 추가 6회 API 요청이 발생한다. 스크립트는 요청별 결과를 즉시 저장하고 6회 모두 정상 완료와 비어 있지 않은 텍스트를 반환하면 종료 코드 0, 그 외에는 1을 반환한다. 환경변수 누락은 API를 호출하지 않고 `not_attempted`로 기록한다.
