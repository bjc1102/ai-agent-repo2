# 1주차 과제

## 1. 수업 정리

### LLM은 어떻게 응답을 만드는가?

**LLM은 입력 문맥과 학습된 패턴을 바탕으로 다음 토큰의 확률을 계산하는 모델이다.** 입력 문장은 **토크나이저**를 통해 **토큰**으로 나뉘고, 모델은 토큰 사이의 관계와 문맥을 처리한다. 이후 **다음 토큰을 선택하고 문맥에 추가하는 과정을 반복**해 답변을 만든다. 일반적인 API 호출은 모델을 다시 학습시키는 것이 아니라 이미 학습된 모델로 응답을 만드는 **추론**이다.

**토큰은 텍스트를 처리하는 단위이며 단어 하나와 반드시 일치하지 않는다.** **Context window**는 한 요청에서 다룰 수 있는 문맥의 범위이고, **출력 토큰 한도**는 이번 응답에 허용한 최대 생성량이다. 출력 한도가 크다고 반드시 길게 답하는 것은 아니지만 너무 작으면 문장이나 JSON이 중간에 끊길 수 있다. 토큰 한도 계산 방식은 사용하는 모델과 API에 따라 확인해야 한다.

### API 호출에는 무엇이 필요한가?

요청에는 사용할 **모델**, 작업과 판단 기준을 설명하는 **지시**, 처리할 **입력**, 원하는 **출력 형식**, **생성 설정**이 필요하다. 예를 들어 고객 문의를 분류한다면 “배송지 변경 요청은 주문변경팀으로 분류한다”는 지시이고, “배송지를 집으로 바꿔주세요”는 입력이다. **지시와 입력을 분리**하면 같은 기준으로 여러 문의를 비교하기 쉽다. **SDK**는 코드에서 API 요청과 응답 처리를 쉽게 할 수 있도록 제공하는 도구다.

**Temperature와 top-p**는 지원되는 모델에서 다음 토큰 후보 선택에 영향을 주지만 **정답률을 직접 조절하는 설정은 아니다.** 모델과 추론 모드에 따라 지원 여부가 다를 수 있으므로 요청이 성공했다는 이유만으로 설정이 적용됐다고 판단해서는 안 된다.

> **핵심 요약:** LLM은 문맥을 바탕으로 다음 토큰을 반복 생성한다. 원하는 결과를 얻으려면 모델·지시·입력·출력 형식·생성 설정을 구분해 요청하고, 응답의 완료 여부·구조·의미를 각각 확인해야 한다.

## 2. LLM의 한계와 보완 방법

### 필요한 지식을 모두 갖고 있지 않다

범용 모델은 특정 기업의 내부 정책, 비공개 자료, 최신 상태를 기본적으로 알지 못할 수 있다. 예를 들어 우리 회사의 환불 정책을 제공하지 않으면 일반적인 관행을 바탕으로 잘못 안내할 수 있다. RAG는 관련 문서를 검색해 요청 문맥에 제공하고, 도구/API 조회는 현재 주문 상태 같은 최신 정보를 가져와 이 문제를 보완한다. 다만 검색한 문서가 잘못됐거나 모델이 근거를 잘못 해석할 수 있으므로 검색과 답변을 함께 검증해야 한다.

### 정확성과 지시 준수를 항상 보장하지 못한다

지시와 자료가 충분해도 모델은 잘못 판단하거나 요청한 형식을 어길 수 있다. 배송지 변경 문의를 환불팀으로 보내는 오류가 그 예다. 명확한 지시와 풀이 예시는 판단 기준을 전달하고, Schema 기반 출력은 구조 오류를 줄이는 데 도움이 된다. 의미 오류는 별도의 업무 규칙 검사, 대표 입력을 이용한 평가, 필요한 경우 사람의 확인으로 보완해야 한다. 구조화 출력만 적용했다고 모든 오류가 해결되는 것은 아니다.

### 문맥의 크기와 활용에 한계가 있다

Context window에는 크기 제한이 있고, 그 범위 안에 넣은 정보도 항상 정확하게 활용하는 것은 아니다. 긴 대화에서 앞부분의 조건을 놓치거나 많은 문서 속 예외 조항을 답변에 반영하지 못할 수 있다. 필요한 부분만 검색해 전달하는 RAG, 대화 요약, 중요한 조건을 별도로 관리하는 방식으로 보완할 수 있다. 다만 검색이나 요약 과정에서 필요한 정보가 빠질 수 있으므로 원문 근거와 중요 조건의 보존 여부를 확인해야 한다.

## 3. LLM 호출 실험

### 실험 목적

고객 문의를 분류할 때 풀이 예시를 제공하면, 분류 기준만 제공했을 때와 결과가 달라지는지 확인했다.

### 실험 방법

- 모델: `gemini-3.5-flash-lite`
- SDK: Google GenAI Python SDK (`google-genai==2.12.1`)
- A 조건: 분류 기준만 제공했다.
- B 조건: A와 같은 분류 기준에 풀이 예시 4개를 추가했다.
- 두 조건에서 모델, 시험 문의, 분류 기준, 출력 JSON Schema, 출력 토큰 한도 4096을 동일하게 유지했다.
- Temperature, top-p, thinking 설정은 별도로 전달하지 않고 제공자의 기본 설정을 사용했다.
- 각 요청은 대화 이력 없이 독립적으로 호출했다. 문의 3개를 조건별로 3회씩, 총 18회 호출했다.
- 기대 결과는 호출 전에 정하고, 정상 완료 여부·구조 적합성·분류 일치를 구분해 검사했다.
- 문의와 풀이 예시는 실험용으로 작성한 가상 데이터다.

### 분류 기준

| 문의 유형 | 담당 부서 |
|---|---|
| 배송지 변경 | 주문변경팀 |
| 배송 지연 또는 도착 시점 문의 | 배송팀 |
| 환불 요청 | 환불팀 |
| 수정 대상 등 의도가 불명확함 | 추가확인 |

`의도 불명확`은 API 오류가 아니다. 고객의 요청을 판단할 정보가 부족해 추가 질문이 필요하다는 정상 분류다.

### 입력과 결과

실제 요청 조건과 메타데이터는 [실험 계획](experiment2_plan.json), 응답 원문과 종료 상태는 [실제 응답 기록](experiment2_responses.jsonl)에 보존했다. 다운로드한 기록 18건을 확인했으며 모두 정상 완료·구조 통과·기대 분류 일치였고 기록된 API 오류는 없었다.

여러 의도 표현과 과거·현재 요청이 함께 있는 문의 3개를 사용했다. A와 B 사이에서는 예시의 유무만 변경하고, 나머지 조건은 동일하게 유지했다.

| 번호 | 입력 | 기대 결과 |
|---|---|---|
| Q1 | 어제는 배송이 늦으면 환불하겠다고 했는데, 환불은 하지 않고 그냥 받겠습니다. 오늘 요청하는 건 받을 주소를 회사에서 집으로 바꾸는 것뿐이에요. | 배송지 변경 / 주문변경팀 |
| Q2 | 처음에는 주소를 잘못 적어서 배송지를 바꾸려 했지만 그 문제는 이미 해결됐어요. 취소나 환불도 원하지 않습니다. 도착 예정일이 지났는데 지금 상품이 어디에 있고 언제 도착하나요? | 배송 지연 / 배송팀 |
| Q3 | 배송지를 바꾸거나 환불해 달라는 뜻은 아니에요. 주문한 내용을 조금 수정하고 싶은데 처리해 주실 수 있나요? | 의도 불명확 / 추가확인 |

| 조건 | 호출 | 정상 완료 | 구조 통과 | 기대 분류 일치 |
|---|---:|---:|---:|---:|
| A: 예시 없음 | 9 | 9 | 9 | 9 |
| B: 예시 있음 | 9 | 9 | 9 | 9 |

#### 관찰

- 복합적인 표현이 포함된 문의에서도 두 조건 모두 9회 전체에서 정상 완료·구조 통과·기대 분류 일치를 충족했다.
- Q1은 과거의 환불 의사를 현재 요청으로 선택하지 않았고, Q2는 해결된 주소 문제 대신 현재 배송 문의로 분류했다.
- Q3는 수정 대상이 불명확하므로 추가확인으로 분류했다. 이는 실패가 아니라 사전에 정한 기대 결과와 일치한다.
- 이번 입력 세트에서도 예시 추가에 따른 분류 결과의 차이를 관찰하지 못했다. 줄바꿈이나 공백 차이는 JSON 값의 차이로 보지 않았다.

### 해석과 한계

**확인한 사실은 예시 없는 조건과 예시 있는 조건 모두 9회 중 9회 기대 분류에 일치했다는 것이다.** 예시 없는 조건부터 전체 정답이어서 정답률로 추가 개선을 관찰할 여지가 없었다. 이는 측정한 정답률에서의 **천장 효과**다.

차이가 없었던 가능한 이유는 다음과 같다.

- **기본 지시가 충분히 구체적이었다.** 분류 기준뿐 아니라 “고객이 부정한 의도는 선택하지 마세요”, “근거가 부족하면 추측하지 마세요”라는 지시를 두 조건에 동일하게 제공했다.
- **현재 모델이 이 입력을 예시 없이도 처리할 수 있었을 가능성이 있다.** 문의에 여러 의도 표현이 섞여 있어도 최종 요청이나 정보 부족을 판단할 단서가 있었고, 별도의 전문 지식은 필요하지 않았다.
- **풀이 예시가 새로운 분류 기준을 추가하지 않았다.** 이미 제시한 규칙을 다른 문장으로 보여주는 예시였으므로, 규칙만으로 판단한 경우에는 결과가 달라지지 않을 수 있다.

따라서 “모델이 똑똑해서”와 “실험이 단순해서” 중 하나를 원인으로 확정할 수는 없다. **현재 모델과 지시의 조합으로 이 세 문의를 처리할 때 예시의 추가 효과가 관찰되지 않았다**고 해석하는 것이 적절하다. 문의가 3개이고 조건별 반복도 3회인 소규모 실험이므로 예시가 일반적으로 불필요하다거나 모델이 모든 문의를 정확하게 처리한다고 일반화할 수 없다.
