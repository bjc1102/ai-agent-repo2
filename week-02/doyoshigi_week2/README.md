# 1. RAG 조사·정리

## 1-1. RAG(Retrieval-Augmented Generation)는 LLM의 어떤 한계를 보완하는가?

- 일반적인 LLM은 앞에 나온 글을 바탕으로 다음에 올 말을 예측하도록 학습한다. 이 과정에서 여러 사실을 익히지만, 학습한 정보를 항상 정확히 재현할 수는 없다. 특정 버전의 매뉴얼에 나온 세부 절차나 학습 이후에 바뀐 정보를 답하려면 별도의 근거가 필요할 수 있다.
- RAG는 **질문과 관련된 자료를 찾아 모델에 함께 제공하고, 그 내용을 바탕으로 답을 생성하는 방식**이다. 이때 모델에 제공하는 문서 발췌가 **컨텍스트**다. 예를 들어 특정 버전의 설치 방법을 물으면, 해당 버전의 매뉴얼에서 설치 절차를 찾아 모델이 그 내용을 근거로 답하게 할 수 있다.

## 1-2. 문서 준비 → 검색 → 컨텍스트 구성 → 답변 생성은 어떻게 이어지는가?

- **문서 준비** — 매뉴얼이나 FAQ에서 텍스트를 추출하고, 필요한 부분을 찾기 쉽도록 정리한다.
- **검색** — 질문이 들어오면 준비한 자료에서 질문과 관련된 문서 조각을 찾는다.
- **컨텍스트 구성** — 검색된 조각 중 모델이 참고할 **원문 텍스트**를 골라 질문과 함께 입력에 넣는다. 출처를 함께 전달하면 나중에 답변의 근거를 확인할 수 있다.
- **답변 생성** — 모델이 질문과 컨텍스트를 읽고 답을 작성한다. 근거가 부족하면 문서에서 확인할 수 없다고 답하도록 지시할 수 있다.

## 1-3. 키워드 기반 검색과 임베딩 기반 검색은 어떻게 다른가?

- **키워드 검색**은 질문과 문서에 등장하는 단어의 일치를 중심으로 관련도를 판단한다. 보통 어떤 단어가 어느 문서 조각에 나오는지 검색 인덱스에 기록해 두고, 질문에 나온 단어를 기준으로 해당 조각을 찾는다. 제품명이나 오류 코드처럼 정확한 표현을 알고 있을 때 유용하다.
- **임베딩 기반 벡터 검색**은 질문과 문서 조각을 각각 벡터로 바꾸고, 벡터가 얼마나 가까운지 비교해 **의미가 비슷한 문서 조각**을 찾는다. 예를 들어 “비밀번호를 잊었다”라는 질문으로, 표현이 다른 “계정 암호 재설정” 문서를 찾을 수 있다.
- 두 방식은 **같은 문서 조각을 대상으로 검색**할 수 있다. 관련도를 판단하는 기준이 다르므로, 같은 질문이라도 실제로 찾아오는 조각과 검색 순위는 달라질 수 있다.

## 1-4. 청킹, 임베딩, 벡터 저장소는 각각 어떤 역할을 하는가?

- **청킹**은 긴 문서를 검색에 사용할 작은 조각으로 나누는 과정이다. 예를 들어 매뉴얼에서 비밀번호 재설정 절차가 담긴 부분을 하나의 검색 단위로 만들 수 있다.
- **임베딩**은 나눈 문서 조각을 숫자 목록인 **벡터**로 바꾸는 과정이다. 기본적인 구성에서는 조각 하나를 벡터 하나로 바꾸고, 질문도 같은 방식으로 벡터화해 두 내용의 의미가 얼마나 가까운지 비교한다.
- **벡터 저장소(Vector Store)**는 문서 조각의 벡터를 저장하고, 질문 벡터와 가까운 조각을 찾는 역할을 한다. 찾은 벡터에 연결된 원문을 가져오면 모델의 컨텍스트로 사용할 수 있다. 벡터 저장소는 RAG의 검색 단계에서 사용할 수 있는 구성 요소다.

## 1-5. RAG를 적용해도 어떤 문제가 남는가?

- **검색에서 근거를 놓칠 수 있다.** 질문과 의미가 비슷한 조각이 검색돼도, 정답이 담긴 조각은 상위 결과에 포함되지 않을 수 있다.
- **문서의 품질이 답변에 영향을 준다.** 오래됐거나 잘못된 자료가 검색되면 모델이 그 내용을 바탕으로 답할 수 있다.
- **모델이 근거를 잘못 사용할 수 있다.** 정확한 문장을 가져와도 잘못 해석할 수 있고, 근거가 부족한데도 답을 단정할 수 있다. 따라서 **검색이 필요한 근거를 찾았는지**와 **모델이 그 근거에 맞게 답했는지**를 따로 확인한다.

# 2. 기본 RAG 실습

## 2-1. 구성 방식과 선택 이유

- **방식** — WSL Ubuntu에 필요한 도구를 설치하고 로컬에서 실행했다.
- **구성** — Python(전체 실행 흐름), SQLite FTS5(키워드 검색), Chroma(벡터 검색), Ollama(모델 실행).
- **선택 이유** — API 키와 결제 설정 없이 내 컴퓨터에서 실습할 수 있어 로컬 방식을 골랐다.
- **구현한 부분** — Python 코드에서 문서 분할, 검색어 추출, 검색 호출, 모델 입력 구성, 결과 저장을 연결했다.

## 2-2. 실습 자료

- **자료** — Python 3.13.0 공식 `venv` 설명서.
- **원본 링크** — <https://raw.githubusercontent.com/python/cpython/v3.13.0/Doc/library/venv.rst>
- **선택 이유** — 검색된 내용이 원문의 어느 줄에 있는지 확인하기 쉽다.

## 2-3. 구현 흐름과 설정

같은 문서, 질문, 답변 모델을 두고 검색 방식만 바꿔 비교했다.

| 단계 | 설정 |
|---|---|
| 문서 준비 | 최대 14줄씩 나누고 3줄씩 겹치게 해 청크 67개를 만들었다. |
| 키워드 검색 | `rag_keyword.py`가 질문에서 검색어를 뽑고, SQLite FTS5가 BM25로 최대 3개를 찾는다. |
| 벡터 검색 | `rag_vector.py`가 `embeddinggemma`로 문서와 질문을 벡터로 바꾸고, Chroma가 코사인 거리가 가까운 청크를 최대 3개 찾는다. |
| 답변 생성 | `rag_common.py`가 검색한 원문과 줄 번호를 질문과 함께 `qwen2.5:3b`에 전달한다. |
| 결과 저장 | 질문, 검색된 청크, 답변을 `results_keyword.json`과 `results_vector.json`에 각각 저장한다. |

## 2-4. 실제 실행 결과

| 질문 | 키워드 검색 | 벡터 검색 |
|---|---|---|
| PowerShell에서 가상환경을 활성화하는 경로는? | 정답이 담긴 청크를 **1위**로 찾았다. 모델은 같은 경로가 나온 3위 청크를 인용했다. | 정답이 담긴 청크를 **3위**로 찾았고, 모델이 그 청크를 인용했다. |
| 기본 Python 패키지를 가상환경에서도 쓰는 옵션은? | 상위 3개에서 `--system-site-packages`를 찾지 못했다. 모델은 “문서에서 확인할 수 없습니다”라고 답했다. | 상위 3개에서 옵션을 찾지 못했다. 모델은 “옵션은 없습니다”라고 잘못 답했다. |
| 가상환경의 기본 저장 용량 제한은? | 일치하는 청크가 없었다. 모델은 확인할 수 없다고 답했다. | 관련 청크 3개를 찾았지만 용량 제한에 관한 내용은 없었다. 모델은 확인할 수 없다고 답했다. |

## 2-5. 확인한 점과 추가로 확인해보고 싶은 사항

- 두 번째 질문의 정답인 `--system-site-packages`는 원본 166–179줄에 있었지만, 두 검색 방식 모두 상위 3개에서 놓쳤다.
- 벡터 검색 실행에서는 모델이 검색 결과에서 옵션을 확인하지 못했는데도 옵션이 없다고 단정했다. **검색이 근거를 찾았는지와 모델이 그 근거에 맞게 답했는지를 따로 확인할 필요가 있었다.**
- 옵션 질문을 영어로 바꿔 두 방식에 다시 넣었을 때, 정답이 담긴 청크가 상위 3개에 들어오는지 확인해보고 싶다.
