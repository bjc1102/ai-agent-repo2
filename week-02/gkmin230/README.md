# AWS GuardDuty 공식 문서 기반 RAG 시스템

## 1. 프로젝트 개요

AWS GuardDuty의 EC2 탐지 유형을 공식 문서에 근거하여 설명하는 RAG(Retrieval-Augmented Generation) 시스템을 구현했다.

사용자가 보안 탐지 유형에 대해 질문하면 Chroma 벡터 데이터베이스에서 관련 문서를 검색하고, GPT-4o-mini가 검색된 내용을 참고하여 한국어 답변을 생성한다.

**프로젝트 목표**
- RAG의 전체 동작 과정 이해
- 공식 문서 수집 및 청킹 구현
- OpenAI 임베딩과 Chroma 벡터 DB 활용
- 검색 결과를 활용한 LLM 답변 생성
- 근거가 없는 질문에 대한 환각 가능성 확인

## 2. RAG 개념 및 필요성

RAG는 외부 지식을 검색하여 LLM의 답변 생성에 활용하는 기술이다.

일반적인 LLM은 학습 시점 이후의 정보나 특정 조직의 내부 데이터를 정확하게 알지 못할 수 있으며, 근거가 부족한 경우에도 그럴듯한 답변을 생성할 수 있다.

RAG는 이러한 문제를 줄이기 위해 질문과 관련된 문서를 검색하고, 검색된 문서를 LLM에 제공한다.

### 기본 동작 과정

1. 문서 수집 및 전처리
2. 문서를 작은 청크로 분할
3. 청크를 임베딩 벡터로 변환
4. 벡터 데이터베이스에 저장
5. 사용자 질문을 임베딩
6. 유사한 문서 검색
7. 검색 문서를 참고하여 답변 생성

RAG는 환각을 줄이는 데 도움이 되지만, 검색 결과가 부정확하거나 LLM이 근거를 잘못 해석하면 오류가 발생할 수 있다.

## 3. 데이터 및 기술 구성

### 데이터 출처

AWS 공식 문서: GuardDuty EC2 finding types

https://docs.aws.amazon.com/guardduty/latest/ug/guardduty_finding-types-ec2.html

수집한 문서의 텍스트 길이는 약 50,968자이다.

### 기술 스택

| 항목 | 사용 기술 |
|---|---|
| 개발 언어 | Python 3.10 |
| 문서 수집 | requests, BeautifulSoup |
| 임베딩 모델 | text-embedding-3-small |
| 벡터 데이터베이스 | Chroma |
| 답변 생성 모델 | gpt-4o-mini |
| 청크 크기 | 800자 |
| 청크 중복 | 100자 |
| 생성된 청크 | 73개 |
| 검색 방식 | 임베딩 기반 벡터 유사도 검색 |
| 검색 개수 | Top-K = 3 |

## 4. 시스템 아키텍처

### 데이터 저장 단계

AWS 공식 문서 → 텍스트 추출 → 청크 분할 → OpenAI 임베딩 → Chroma 저장

### 질문 응답 단계

사용자 질문 → 질문 임베딩 → Chroma 유사도 검색 → 관련 청크 3개 반환 → GPT-4o-mini 답변 생성

문서와 질문에는 동일한 임베딩 모델을 사용했다.

## 5. 구현 과정

### 문서 수집

`download_docs.py`에서 AWS 공식 문서를 요청하고 BeautifulSoup으로 텍스트를 추출했다.

### 청킹

`chunk_docs.py`에서 고정 길이 청킹을 사용했다.

- 청크 크기: 800자
- 중복 길이: 100자
- 전체 청크 수: 73개

중복 영역은 인접한 청크 사이에서 문맥이 일부 유지되도록 하기 위해 설정했다.

### 임베딩 및 저장

`embed_docs.py`에서 OpenAI 임베딩 API를 호출해 73개 청크를 벡터로 변환했다.

이후 Chroma에 벡터, 원본 텍스트, 출처 URL, 청크 번호를 저장했다.

### 검색 및 답변 생성

`rag.py`에서 사용자 질문을 임베딩한 뒤 관련성이 높은 청크 3개를 검색했다.

검색된 문서를 GPT-4o-mini에 제공하고, 문서에 근거하여 한국어로 답하도록 지시했다.

근거가 부족하면 추측하지 않고 확인할 수 없다고 답하도록 프롬프트를 구성했다.

## 6. 실험 결과

### 실험 1: SSHBruteForce

**질문:** SSHBruteForce 탐지는 무엇을 의미하나요?

- 검색 청크: 67, 66, 69
- 결과: EC2 인스턴스와 관련된 SSH 무차별 대입 공격의 의미 및 대응 방법 설명

### 실험 2: Portscan

**질문:** Portscan 탐지는 무엇을 의미하나요?

- 검색 청크: 43, 44, 10
- 결과: 여러 포트에 대한 연결 시도와 포트 스캔 행위 설명

### 실험 3: 답변할 수 없는 질문

**질문:** 어제 우리 회사에서 발생한 GuardDuty 탐지 건수는?

- 검색 청크: 52, 0, 34
- 실제 GPT 답변: "제공된 문서만으로는 확인할 수 없습니다."

AWS 공식 문서에는 특정 회사의 실제 탐지 건수가 없기 때문에, 이 응답은 적절하다고 판단했다.

세 실험의 검색 문서 본문, 거리 점수, 최종 답변은 `results.json`에 기록했다.

## 7. 한계점 및 개선 방향

### 고정 길이 청킹의 한계

800자 단위로 문서를 분할하면서 일부 문장이 중간에 끊기는 문제가 발생했다.

향후 문단이나 제목을 기준으로 분할하는 방식으로 개선할 수 있다.

### 문서 추출 품질

HTML에서 텍스트를 추출하는 과정에서 불필요한 줄바꿈과 목차 정보가 포함되었다.

본문 영역을 더 정확하게 추출하고 전처리하는 과정이 필요하다.

### 검색 품질

Top-K 3으로 검색했지만, 관련성이 낮은 문서가 포함될 가능성이 있다.

향후 키워드 검색과 벡터 검색을 결합한 하이브리드 검색, 재순위화(Reranking)를 검토할 수 있다.

### 환각 가능성

LLM에 문서 기반 답변을 지시하더라도 모든 오류가 제거되는 것은 아니다.

특히 탐지 유형별 심각도나 세부 조건은 원문과 비교하여 검증해야 한다.

### 보안 고려사항

외부 문서에 악의적인 지시가 포함되면 프롬프트 인젝션이 발생할 수 있다.

따라서 검색 문서는 신뢰할 수 없는 데이터로 취급하고, LLM의 시스템 지시와 구분해야 한다.

## 8. 실행 방법

Python 3.10 환경에서 실행한다.

### 패키지 설치

```bash
python -m pip install chromadb openai python-dotenv requests beautifulsoup4
```

### 환경변수 설정

프로젝트 루트에 `.env` 파일을 생성한다.

```text
OPENAI_API_KEY=본인의_API_키
```

실제 API 키가 포함된 `.env` 파일은 GitHub에 업로드하지 않는다.

### 실행 순서

```bash
python download_docs.py
python chunk_docs.py
python embed_docs.py
python search_docs.py
python rag.py
```

실행 후 `results.json`에 3개 질문의 검색 결과와 답변이 저장된다.

## 9. 결론

이번 프로젝트를 통해 문서 수집부터 청킹, 임베딩, 벡터 검색, LLM 답변 생성까지 RAG의 전체 흐름을 구현했다.

특히 보안 관제에서 활용하는 GuardDuty 탐지 유형을 주제로 선정하여 실무와 연결되는 사례를 실험할 수 있었다.

답변할 수 없는 질문에 대해서는 정보 부족을 명시하는 결과를 확인했다. 다만 한 번의 성공적인 실험만으로 환각이 완전히 방지된다고 판단할 수는 없으며, 향후 검색 품질 개선과 반복 평가가 필요하다.
