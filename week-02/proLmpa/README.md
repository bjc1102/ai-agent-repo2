## 1. RAG란?

### 1-1. RAG의 정의 & 필요성

LLM은 지식을 두 가지 방식으로 보유한다.

| 종류 | 설명 | 특징 |
|------|------|------|
| **Parametric memory** (가중치) | 사전 학습 시 가중치에 압축된 지식 | 빠르지만 업데이트 불가, 출처 불명확 |
| **Non-parametric memory** (컨텍스트) | 입력 프롬프트에 직접 주입되는 텍스트 | 최신·특정 문서 활용 가능, 토큰 비용 발생 |

RAG(Retrieval-Augmented Generation)는 질문 시점에 관련 문서를 검색하여 컨텍스트로 주입함으로써, LLM의 non-parametric memory를 동적으로 확장하는 아키텍처다.

**LLM 단독 사용의 5가지 한계와 RAG의 역할:**

| 한계 | 문제 | RAG 효과 |
|------|------|-----------|
| 환각(Hallucination) | 없는 사실을 그럴듯하게 생성 | 검색된 문서 근거로 답변 범위 한정 |
| 출처 불명확 | 어느 자료를 근거로 했는지 알 수 없음 | 청크 메타데이터(source, page)로 출처 명시 가능 |
| 지식 노후화 | 학습 컷오프 이후 정보 없음 | 최신 문서를 인덱스에 추가하면 즉시 반영 |
| 지식 수정 어려움 | 오류 수정에 재학습 필요 | 문서 교체·재인덱싱으로 수정 가능 |
| 맞춤화 한계 | 도메인 특화 지식 부재 | 사내 문서·전문 자료를 인덱스로 주입 |

---

### 1-2. RAG 파이프라인 전체 흐름

RAG는 크게 **오프라인 단계(인덱싱)**와 **온라인 단계(질의·생성)**으로 나뉜다.

```
[오프라인] 문서 준비
  ① 문서 로드 → ② 청킹(분할) → ③ 임베딩(벡터화) → ④ Vector Store 저장

[온라인] 질의 처리
  ⑤ 쿼리 임베딩 → ⑥ 유사도 검색(top-k) → ⑦ 컨텍스트 구성 → ⑧ LLM 답변 생성
```

| 단계 | 역할 | 단계별 실패 예시 |
|------|------|-----------------|
| 청킹 | 문서를 검색 단위로 분할 | 고정 크기 청킹이 Q&A 쌍을 쪼개어 답변 청크에 핵심 단어 누락 |
| 임베딩 | 텍스트를 벡터 공간에 매핑 | 모델이 도메인 용어를 범용 단어로 처리해 유사도 왜곡 |
| Vector Store 저장 | 벡터 인덱스 디스크 유지 | 문서 변경 후 재인덱싱 미수행으로 오래된 청크 반환 |
| top-k 검색 | 쿼리와 가장 가까운 k개 청크 반환 | TOC·목차 페이지가 실제 답변 페이지보다 높은 유사도 획득 |
| 컨텍스트 구성 | 청크를 프롬프트에 삽입 | top-k가 너무 작으면 정답 청크 누락, 너무 크면 노이즈 증가 |
| 답변 생성 | LLM이 컨텍스트 기반으로 응답 | 시스템 프롬프트 미설정 시 문서 외 추론이 답변에 혼입 |

### 1-3. RAG 용어

**핵심 용어 정의:**

| 용어 | 정의 |
|------|------|
| **Chunking** | 긴 문서를 검색 단위(청크)로 분할하는 과정. 크기·오버랩·분할 기준에 따라 검색 품질이 결정됨 |
| **Embedding** | 텍스트를 고차원 실수 벡터로 변환. 의미적으로 유사한 텍스트는 벡터 공간에서 가깝게 위치 |
| **Vector Store** | 임베딩 벡터와 메타데이터를 저장하고 유사도 검색을 지원하는 데이터베이스 |
| **Retriever** | 쿼리를 입력받아 관련 청크를 반환하는 검색 모듈 |
| **Generation** | 검색된 청크를 컨텍스트로 LLM에 전달해 최종 답변을 생성하는 단계 |

**키워드 기반 vs 임베딩 기반 검색 비교:**

| 방식 | 강점 | 위험 |
|------|------|------|
| **키워드(BM25)** | 정확한 단어 매칭, 도메인 용어·고유명사에 강함 | 동의어·유사 표현을 놓침 |
| **임베딩(Dense)** | 의미적 유사도 포착, 구어체·다양한 표현 처리 | 단어 불일치(예: "선택병의원" vs "선택의료급여기관") 시 유사도 왜곡 가능 |
| **하이브리드** | 두 방식의 점수를 결합(RRF 등)하여 약점 보완 | 구현 복잡도 증가 |

**Contextual Retrieval (Anthropic, 2024):**
각 청크를 임베딩하기 전에 LLM으로 "이 청크가 문서 전체 맥락에서 어떤 내용인지"를 설명하는 짧은 문장을 생성하여 청크 앞에 붙이는 방식. 문서 맥락을 잃어버리는 고정 크기 청킹의 한계를 완화한다.

---

### 1-4. RAG 적용 시 한계

| 범주 | 한계 | 설명 |
|------|------|------|
| 지식 범위 | 인덱스 커버리지 한계 | 문서에 없는 내용은 아무리 검색 품질이 좋아도 답변 불가 |
| 검색 | 청킹 품질 의존성 | 분할 전략이 나쁘면 정답이 문서에 있어도 검색 실패 |
| 검색 | 쿼리-문서 용어 불일치 | 사용자 표현과 문서 표현이 다르면 유사도 하락 |
| 근거 사용 | 컨텍스트 오염 | TOC·면책조항 등 비정보 청크가 top-k에 포함되어 답변 품질 저하 |
| 답변 범위 | 시스템 프롬프트 경계 초과 | LLM이 컨텍스트 외 사전 지식으로 추론을 혼입 |
| 신뢰·실무 정확도 | 검색 실패와 문서 미수록 구분 불가 | 두 경우 모두 "문서에 없다"는 동일 응답으로 처리됨 |
| 평가 | 자동 평가 어려움 | 정답이 명확하지 않은 질문에 대한 답변 품질 측정이 어려움 |

## 2. RAG 실습

### 2-1. 데이터(자료) 선정 이유

**직접 설치(Self-hosted)** 방식을 선택했습니다.

| 컴포넌트 | 선택 | 이유 |
|----------|------|------|
| Vector Store | ChromaDB (persistent) | pip 설치만으로 동작, 별도 서버·클라우드 계정 불필요, 인덱스 디스크 저장 |
| 임베딩 모델 | `paraphrase-multilingual-mpnet-base-v2` | 로컬 실행, 한국어 지원, 완전 무료 |
| LLM | Claude claude-sonnet-4-6 (Anthropic API) | 기존 API 키 재사용, 한국어 고품질 답변 |
| PDF 파싱 | pdfplumber | 한국어 PDF 텍스트 추출 안정적 |

외부 벡터 DB 서비스나 별도의 임베딩 API 없이 로컬에서 전 과정이 실행되므로, 비용·네트워크 의존성을 최소화할 수 있습니다.

**사용 데이터:**

| 항목 | 내용 |
|------|------|
| 파일명 | `2024 알기 쉬운 의료급여제도.pdf` |
| 출처 | 보건복지부 / 국민건강보험공단 발간 공식 안내 자료 |
| 페이지 수 | 약 40페이지 |
| 내용 요약 | 의료급여 1·2종 구분, 본인부담금, 선택병의원 제도, 정신과 입원 절차, 급여 제외 항목 등 |

한국어 텍스트가 풍부하고 구조적인 내용(표·목록)을 포함해 RAG의 청킹·검색 성능을 평가하기에 적합합니다.

---

### 2-2. 실험 구성

#### RAG 처리 흐름

```
PDF 파일
   │
   ▼
[1] 문서 로드 (pdfplumber)
   페이지별 텍스트 추출, 빈 페이지 스킵
   │
   ▼
[2] 청킹
   500자 단위 분할, 100자 오버랩
   메타데이터 부착: {source, page, chunk_id}
   │
   ▼
[3] 임베딩 & 인덱싱
   SentenceTransformer 로컬 모델로 배치 인코딩
   ChromaDB PersistentClient로 디스크 저장 (chroma_db/)
   │
   ▼  rag_basic.py 여기까지 실행

[4] 검색 (Retrieval)          ← query.py 는 chroma_db/ 를 로드
   쿼리 임베딩 → ChromaDB cosine 유사도 검색
   top_k 청크 반환 (기본 3, --top-k 로 조정 가능)
   │
   ▼
[5] 답변 생성 (Generation)
   검색된 청크를 컨텍스트로 Claude API 호출
   "문서 내용만 근거로 답변" 시스템 프롬프트
   │
   ▼
최종 답변 출력
```

#### 주요 설정값

| 파라미터 | 값 | 설명 |
|----------|----|------|
| `CHUNK_SIZE` | 500 | 청크 최대 문자 수 |
| `CHUNK_OVERLAP` | 100 | 인접 청크 간 오버랩 문자 수 |
| `TOP_K` | 3 | 검색에서 반환할 청크 수 |
| `EMBEDDING_MODEL` | `paraphrase-multilingual-mpnet-base-v2` | 로컬 임베딩 모델 |
| `max_tokens` | 1024 | Claude 응답 최대 토큰 |

#### 실행 방법

```bash
# 1. 의존성 설치
pip install -r requirements.txt

# 2. 인덱스 빌드 + 테스트 질문 4개 실행 (chroma_db/ 생성)
python rag_basic.py

# 3. 대화형 질의 (rag_basic.py 실행 후 사용 가능)
python query.py

# top_k 조정 예시
python query.py --top-k 5
```

### 2-5. 한계 및 개선점

#### 검색(Retrieval) 단계

| 한계 | 실제 사례 | 개선 방향 | 난이도 |
|------|-----------|-----------|--------|
| 고정 크기 청킹 — Q&A 쌍·문단 경계 무시 | 틀니 Q48 질문과 답변이 서로 다른 청크로 분리 | `Q숫자.` 패턴 기준 의미 단위 청킹 | 높음 |
| 표(table) 구조 소실 — `extract_text()`가 행을 평탄화 | 1종/2종 비교표가 의미 없는 문자열로 추출됨 | `extract_tables()` API로 별도 추출 후 자연어 문장 변환 | 중간 |
| 쿼리-문서 용어 불일치 | "선택병의원" vs 문서의 "선택의료급여기관" | 검색 전 쿼리 정규화 dict 적용 | 낮음 |
| TOP_K 고정 — 정답 청크가 순위권 밖에 있으면 영구 누락 | 틀니 정답 청크가 4위 이하로 밀림 | TOP_K를 5~7로 증가 (토큰 비용 증가 감수) | 낮음 |
| 단순 cosine 유사도 — 키워드 매칭 약함 | 구어체 쿼리의 낮은 유사도 | BM25 하이브리드 검색 또는 reranker 추가 | 높음 |

#### 생성(Generation) 단계

| 한계 | 실제 사례 | 개선 방향 | 난이도 |
|------|-----------|-----------|--------|
| 검색 실패와 문서 미수록을 구분 불가 | 틀니(검색 실패)와 성형수술(미수록) 모두 동일하게 "없다"고 답변 | 유사도 임계값 기반 신뢰도 신호를 프롬프트에 포함 | 낮음 |
| 시스템 프롬프트 경계 초과 — 문서 외 추론 소량 포함 | 성형수술 답변에서 "비급여 가능성 높다" 추론 | 프롬프트에 "추론·가능성 표현 금지" 명시 | 낮음 |
