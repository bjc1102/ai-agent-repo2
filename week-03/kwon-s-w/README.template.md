# Gemma RAG 평가 — 정리본

기존 수도권 신규택지 보도자료·청크·질문 5개와 Gemma를 사용한다. 누적된 수정 코드를 제거하고 **검색 → 답변 생성 → 평가 → 사람 확인 → 저장**의 한 흐름으로 정리했다. 기존 노트북이나 패치 파일을 먼저 실행할 필요가 없다.

## 평가 목적과 성공 기준

평가의 목적은 문서에 관한 질문을 실제로 해결하는지 확인하고, 실패가 문서 처리·검색·근거 활용·출력 중 어디에서 생겼는지 판단하는 것이다. 일반적인 모델 순위를 정하려는 실험은 아니다.

문서로 답할 수 있으면 필요한 사실을 정확하게 답하고, 답할 수 없으면 확인 불가를 안내한다. 일부만 알 수 있으면 알려진 내용과 모르는 내용을 구분한다. 핵심 답이 맞아도 틀린 부연을 붙이면 완전 성공으로 보지 않는다. 목표·계획을 확정·완료로 바꾸거나 다른 지역 설명을 섞는 것도 실패다.

검색에서는 필요한 근거가 후보 목록과 실제 최종 요청에 들어갔는지 확인한다. 생성에서는 근거와 일치하는지, 요구를 빠뜨리지 않았는지, 알 수 없는 값을 만들지 않았는지 확인한다. 실행 완료는 정답 판정이 아니다.

자동 지표만으로 충분하지 않다. 필수 표현이 있어도 틀린 부연이 남을 수 있고, LLM Judge도 대상·시점·부정 표현을 잘못 해석할 수 있다. 생성과 Judge를 같은 Gemma로 수행하므로 독립적인 검증이 아니다. 질문 다섯 개를 사람이 원문과 대조한다. 이 구분은 지정 [Stanford 영상](https://www.youtube.com/watch?v=8fNP4N46RRo)과 [공식 Lecture 8 슬라이드](https://cme295.stanford.edu/slides/fall25-cme295-lecture8.pdf)의 평가 목적·기준·Judge 한계를 실습에 적용한 것이다. 영상을 직접 시청하거나 자막을 추출했다는 뜻은 아니다.

| ID | 유형 | 질문 | 기대 답변 | 근거 |

| E4 | 답변 불가 | 김포아라 84㎡ 확정 분양가는? | 제공된 자료로 확인 불가 | PDF 전체에서 해당 가격 미기재 |

생성 코드는 `data/questions.json`의 ID와 질문만 읽는다. 기대 답변·근거 그룹·답변 가능 여부·검사용 표현은 평가 셀에서 별도 파일로 준비하며 검색 색인이나 답변 생성 입력에 넣지 않는다.

## 자료와 구현

자료는 국토교통부 「수도권 신규택지 10.4만호 신속 공급」 보도자료(PDF 6쪽, 2026-10-29)다. [공개 출처](https://www.korea.kr/briefing/pressReleaseView.do?newsId=156786992). 공급량·목표·정보 미기재 질문을 함께 만들 수 있어 선택했다. 기존 제출본에서 공개자료 담당자 성명·연락처 등을 가린 추출문과 **동일한 29개 청크**를 재사용하며 새 OCR·재청킹을 하지 않는다. 자료 출처와 해시는 `data/source_metadata.json`에 기록했다.

| 항목 | 구성 |
|---|---|
| 실행 | Google Colab GPU, Ollama. 실제 버전·모델 digest는 실행 결과에 기록 |
| 생성 모델 | `gemma3:4b`, temperature=0, seed=42, num_ctx=8192, num_predict=600 |
| 임베딩/저장소 | `embeddinggemma`, Chroma 1.5.9, cosine |
| 기존 청크 설정 | 문단 우선 본문 최대 900자, 이전 문장 최대 120자 겹침. 청크 29개 재사용 |
| 검색 | 벡터 후보 6개 + 기존 BM25 후보 6개, RRF k=60 |
| 실제 입력 | 최대 8개 청크, 4,200자 예산, 질문 분해 없음 |
| 생성 방식 | 질문에 필요한 1~2문장만 일반 텍스트로 생성. 계산ID·출처ID 출력 요구 없음 |
| 평가 | Ragas 0.4.3, 호환용 langchain-community 0.4.1 고정, 동일 Gemma Judge |

검색된 문서의 ID·페이지는 프로그램이 별도로 저장한다. 이것을 답변의 각 문장이 검증됐다는 인용으로 표시하지 않는다. 최종 답변을 출처 형식 오류로 숨기지 않는다. 빈 답변·통신 오류·잘림은 원 응답과 함께 기록하고 평가를 보류한다. 길거나 질문을 반복한 답변은 경고를 남기되 내용을 잘라내거나 정답으로 바꾸지 않는다.

문서 추출·청킹 설정은 기존 실습을 사용하고 색인·검색·입력 구성·호출·저장은 직접 구현했다. Ollama가 모델 추론, Chroma가 벡터 저장과 검색, Ragas가 지표 계산을 처리한다. 외부 유료 생성 API나 API 키를 사용하지 않는다. 모델 태그가 같아도 실제 가중치나 실행 환경이 동일하다고 가정하지 않고 기록한다.

## 프레임워크와 지표

Ragas는 검색과 생성을 분리해 평가할 수 있어 선택했다. [DeepEval](https://deepeval.com/docs/getting-started)은 테스트·CI 연계, [TruLens](https://www.trulens.org/getting_started/core_concepts/rag_triad/)는 관련성·근거성 진단 관점으로 검토했지만 이번에는 추가 설치하지 않는다. 검색 구성도 벡터 단독·BM25 단독·재순위화와 비교할 수 있으나, 이번 정리본은 기존 검색 설정을 유지한다.

| 지표 | 입력·의미 | 한계 |
|---|---|---|
| Ragas IDBasedContextRecall | 필요한 근거 그룹이 검색·전달된 비율. 같은 사실의 중복 청크는 대체 가능한 ID로 묶음 | 근거의 의미 활용·정답 여부를 증명하지 않음 |
| 필수요소 포함률 | 평가용 정답의 값·표현이 답변에 있는지 Python으로 검사. E5는 공급량과 정보 부족 안내를 따로 검사 | 전체 정답률이 아니며 동의어를 놓치거나 틀린 부연을 검출하지 못할 수 있음 |
| Ragas Faithfulness | 실제 요청에 전달된 원문으로 답변의 사실 주장이 뒷받침되는지 Gemma Judge가 평가 | 완전성·관련성과 별개이며 Judge도 틀릴 수 있음 |
| 사람 판정 | 원문·실제 검색 결과·입력·답변을 대조해 충족/부분/실패/실행 오류와 이유 기록 | 실제 대조를 수행해야 하며 자동 점수로 대신하지 않음 |

답변 불가 문항의 Recall은 적용 불가다. 새 수치·추가 사실이 없는 단일 정보 부족 안내에는 일반 사실 Faithfulness를 적용하지 않고 안내 요소와 사람이 확인한다. 일부 가능 답변이나 새 가격·날짜를 포함한 답변을 이 예외로 숨기지 않는다. 오류·적용 불가는 `null`과 이유로 저장하고 평균에는 측정 문항 수를 명시한다. 불안정했던 별도 Task Completion Judge의 0/1 총점은 이 정리본에서 사용하지 않는다.

실제 최종 요청에서 컨텍스트를 다시 추출해 선택 청크·기록된 컨텍스트·해시와 일치하는지 검사한다. 별도 검색 결과가 전달 입력과 같다고 가정하지 않는다. 보존하는 것은 실제 API 요청이며 모델 내부에서 모든 문장을 이해했다는 증거는 아니다.

## 실행 방법

`gemma_rag_evaluation_clean.ipynb`를 새 Colab 노트북으로 열고 GPU 런타임을 선택한다. **1 환경 준비 → 2 RAG 실행 → 3 평가 → 4 사람 확인 → 5 다운로드** 순서로 실행한다. 노트북에 기존 자료가 들어 있어 PDF나 Python 패치 파일을 업로드하지 않는다. 패키지는 Colab 안의 별도 가상환경에 설치한다. 예전 노트북과 결과 폴더는 사용하지 않는다.

2번을 다시 실행하면 새 실험을 만든다. 같은 결과의 3번을 다시 실행하면 동일 입력·동일 평가 버전의 점수를 재사용한다. 4번에서는 다섯 판정과 이유, 대표 사례의 원문→검색→생성→정보 부족 판단→자동 평가 대조→우선 개선을 직접 기록한다. 5번 ZIP에는 README·코드·노트북·입력 데이터·실제 요청/응답·평가 이유·사람 판정·단계별 토큰 사용량이 들어가며 벡터 DB·가상환경은 제외한다.
