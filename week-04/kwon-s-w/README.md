# 4주차: Gemma Advanced RAG 비교

기존 3주차 RAG의 검색 기록과 실제 전달 컨텍스트를 보존하는 구조를 유지하고, 문서 구분·복수 근거 확보를 개선 대상으로 정했다. 기준선, 재순위화, 질문 분해를 독립적으로 비교한다. 모델의 정답을 미리 가정하지 않으며 사람의 원문 대조 후 적용 여부를 판단한다.

## GPU 통합본의 오류 수정

- `embeddinggemma`와 `embeddinggemma:latest`를 같은 모델 태그로 확인한다. `gemma3:4b`와 다른 명시적 태그는 구분한다.
- 1번에서 정한 경로를 `/content/week04_gpu_project_path.txt`에 저장하고 이후 셀이 이를 검증해 사용한다. 경로를 임의로 추측하지 않는다.
- 모델명 수정 파일·CPU 준비 ZIP·이전 결과 ZIP은 사용하지 않는다. 내장 자료 복원 셀은 기본 접힘으로 두어 첫 설정 셀을 짧게 유지한다.
- Colab의 GPU 배정 실패는 코드 실행 전의 서비스 자원 문제이며 이 노트북으로 강제할 수 없다. 첫 셀에서 실제 GPU를 확인하고, 5번에서 실제 모델 실행을 확인한 뒤 비교한다.

## 평가 보완과 데이터

- 기존 E3의 `’30년`은 사실 오류가 아니라 표현 명확성 문제였다. 사실 근거와 연도 표기 명확성을 분리해 검사한다. 요구 연도 2030을 명시해야 하는 문항과 축약 연도 출현 여부를 확인한다.
- E5의 `확정 입주일은 자료에 나와 있지 않습니다`는 올바른 안내였지만 이전 정규식이 놓쳤다. `나와 있지 않다`, `기재되지 않았다` 등 표현과 부정의 부정 예문을 검사했다. 필수요소 검사는 완전한 의미 평가가 아니며 사람 판정을 대체하지 않는다.
- 자동 평가 기준은 실행 전에 고정하며, 생성 모델은 `questions.json`의 ID·질문과 검색 문서만 읽는다. 기대 답변·라벨·근거 그룹은 평가 코드에서만 읽는다.
- 문서: 국토교통부 2023-11-15 신규택지 8만호(6쪽), 2024-11-05 신규택지 5만호(5쪽), 기존 2026-10-29 신규택지 10.4만호(6쪽). 총 17쪽·44청크다.
- 2023·2024 PDF는 KDI의 원 보도자료 첨부 PDF로 확보했다. 2026 PDF의 SHA256은 3주차 자료와 대조했다. 문서 URL·다운로드 URL·PDF 해시는 `data/documents.json`에 있다. 추출문은 `data/pages.json`, PDF 원문은 `data/pdf/`에 있다.
- 기존 2026년 청크 29개는 정확히 재사용한다. 추가 PDF는 pdfplumber로 추출한 문단을 페이지 내 최대 900자로 묶었으며 겹침은 추가하지 않았다. 연락처 전용 2쪽은 검색에서 제외하고 원문 검토 자료에는 보존한다. 이 공통 전처리는 세 구성에서 같다.
- 2024 고양대곡은 선택한 보도자료 **본문의 0.9만호**를 기준으로 한다. 다른 기사/자료의 9,400호를 정답에 혼합하지 않는다.
- 5문항: 답변 가능 3개, 답변 불가 1개, 일부 가능 1개. 질문·기대 답변·근거 인용·청크 ID 대안은 `data/references.json`에 있다. 기존 E2/E3/E4/E5의 확인 항목을 재구성하고 사업 비교를 추가했으므로 지난주 점수와 직접 비교하지 않는다. 기존 답변의 평가 규칙 재검사만 별도 감사 기록으로 남긴다.

## 방법 조사와 선택

다른 후보로 메타데이터 필터링, 질문 재작성/멀티쿼리, 부모 문서 확장, HyDE, 문맥 보강 검색이 있다. 현재 기준선은 이미 벡터+BM25 검색이므로 하이브리드를 새로운 기법으로 세지 않는다.

| 구성 | 개선 대상과 동작 | 예상 효과 | 비용·실패 가능성 |
|---|---|---|---|
| 기준선 | 3주차의 벡터+BM25 검색과 RRF 순위 통합 유지 | 늘어난 문서에서 기존 동작 관찰 | 비슷한 사업/연도 혼동, 한쪽 근거 누락 |
| 재순위화 | 같은 최초 후보를 질문-문서 쌍으로 BGE가 다시 평가 | 덜 적합한 후보보다 필요한 근거를 먼저 전달 | CPU 메모리·모델 다운로드·추론 지연, 잘못된 재정렬, 최초 후보 누락은 복구 불가 |
| 질문 분해 | Gemma가 질문을 최대 3개 검색 질문으로 분해하고 원 질문도 유지해 검색, RRF 통합 | 복수 문서에서 필요한 근거를 골고루 확보 | 분해용 호출·임베딩·검색 증가, 사업명/연도 훼손, 제한된 컨텍스트에서 다른 근거를 밀어낼 수 있음 |

재순위화와 질문 분해는 각각 검색 후 순서와 검색 전 질문을 바꾸므로 독립적으로 비교할 수 있다. B는 A를 포함하지 않는다. 질문 분해는 중간 답변을 만들지 않고 실제 검색 근거를 모아 최종 답변 한 번을 생성한다. 단순 질문으로 판단해 빈 분해 결과를 반환한 경우 미적용임을 기록한다. 잘못된 구조/새 수치 도입은 숨겨서 원 질문으로 대체하지 않고 실행 오류로 기록한다.

## 고정 조건과 공통 변경

- 생성 `gemma3:4b`, 임베딩 `embeddinggemma`, Chroma cosine, BM25, RRF k=60.
- 각 검색 질의의 벡터 후보 6개·BM25 후보 6개. 최종 최대 8청크·4,200자. 4,200토큰이라는 뜻이 아니다.
- temperature=0, seed=42, num_ctx=8192, num_predict=600. 3주차 답변 프롬프트 유지. 연도 표현을 강제로 보정해 모델 답변을 수정하지 않는다.
- 문서 수 증가에 맞춰 컨텍스트에 문서 ID·발표일·페이지를 공통 표기했다. 자료/질문/헤더 확장은 지난주 대비 공통 변경이며, 확장한 기준선을 새로 실행한다.
- 재순위화 모델은 `BAAI/bge-reranker-v2-m3`, CPU, batch=2, 최대 입력 1024토큰. 후보별 잘림 여부와 모델 revision을 기록한다. 재개 시 동일 revision을 사용한다.
- 질문 분해에만 별도 Gemma 호출이 있다. 분해 후 원 질문을 포함해 최대 4번 검색하되 최종 컨텍스트 한도는 같다. 평가 기준은 분해 입력에 넣지 않는다.
- 하나의 문항마다 구성 실행 순서를 회전한다. 공통 임베딩 인덱스·모델 로드·워밍업은 준비 단계에 별도 기록한다. RAG 시간은 준비가 끝난 상태의 문항 처리 시간이며 분해/재순위화/검색/생성을 포함한다.
- 문항별 1회이므로 통계적 유의성이나 일반적 성능 우위를 주장하지 않는다. 재시도는 기본 OFF이며 명시적으로 켠 경우 이전 응답·호출도 보존한다.
- 시작할 때 코드·자료·평가 기준 해시를 고정한다. 변경 후 기존 실험에 결과를 섞지 않는다. 모델 digest·패키지 버전·재순위화 revision도 보존한다.

## 평가 지표와 판정

1. **Ragas IDBasedContextRecall**: 기대 근거 그룹 중 후보/실제 전달 청크에 포함된 그룹 비율. 대안 청크 중 하나면 해당 그룹을 찾은 것으로 센다. 의미 정확성이나 불필요한 컨텍스트 비율은 측정하지 않는다. 답변 불가 문항에는 긍정 근거 그룹이 없어 적용 불가다.
2. **필수요소 포함률**: 필요한 수치·목표 표현·확인 불가 안내의 규칙 기반 보조 검사. 여러 사업 수치는 사업명 이후 다음 사업명 이전의 구간에서 확인해 단순 수치 뒤바뀜을 검사한다. 동의어·표·생략 표현 등은 여전히 놓칠 수 있으며 여분의 거짓 주장까지 증명하지 않는다.
3. **연도 명확성**: 요구한 연도를 4자리로 쓰는지, 축약 연도를 쓰는지 확인한다. 연도 사실 자체의 정확성은 근거 평가/사람이 확인한다. 연도 없는 문항은 적용 불가일 수 있다.
4. **Ragas Faithfulness**: 실제 답변의 검증 가능한 사실 주장이 실제 전달 컨텍스트에 의해 지지되는지 Gemma가 평가한다. 기대 답변은 이 평가의 입력이 아니다. 완전성·거절 적절성·전체 정답률이 아니다. 순수 정보 부족 안내에는 적용 불가다. 같은 Gemma가 생성과 평가를 맡는 편향과 구조화 응답 오류가 가능하다.
5. **사람 판정**: 원문·사업/연도·전체/부분·계획/확정·요구사항 충족·불필요한 주장·표현 명확성을 대조한다. 자동 점수와 다를 때 이유를 적는다. 필요한 근거/답변 해결 여부가 최종 판단 기준이다.

원문에 근거가 있는지 → 최초 검색이 찾았는지 → 최종 컨텍스트에 남았는지 → 모델이 올바로 사용했는지 → 답변 가능 여부를 구분했는지 순서로 실패를 분석한다. 대표 실패 문항과 기존에 충족했던 확인 항목의 회귀도 함께 확인한다.

## 실행과 백업

Colab에서 `gemma_rag_week04_gpu_clean.ipynb`의 1~9번을 순서대로 실행한다. PDF·API 키·추가 Python 파일 업로드가 필요 없다. 새 문서 추출문과 PDF·코드는 노트북에 포함된다.

1. GPU 할당 확인·저장 위치 선택. 기본 Drive 저장이며 이전 폴더와 분리한다.
2. 노트북 안의 코드·PDF·평가 기준을 복원한다. 추가 업로드는 없다.
3. 패키지·Ollama·모델을 설치하고 설치된 모델 목록을 표시한다.
4. 다섯 질문·기대 답변 확인, 기준 고정·공통 인덱스 준비.
5. 실제 소규모 임베딩/생성 요청과 Ollama GPU 사용을 확인한다. 품질 점수에 포함하지 않는다.
6. 기준선·재순위화·질문 분해의 총 15개 결과를 실행·저장한다.
7. 동일 평가 기준으로 자동 평가한다.
8. 사람 판정·대표 사례·두 기법 적용 여부를 저장한다.
9. 모델 호출 없이 README·노트북·실제 결과를 ZIP으로 내려받는다.

`.ipynb` 출력에 답변이 남는 것은 실행 결과 저장이며, 실행 환경 파일의 영구 백업과는 다르다. Drive를 사용하지 않으면 런타임 삭제 시 결과를 잃을 수 있다. 환경 재연결 시 1번을 다시 실행해 코드/패키지를 복구한 뒤 2번 준비를 재개한다. 결과 파일을 지우거나 새 실험으로 바꾸지 않는다.

원시 자료와 실제 요청·응답은 `data/`, `results/실행ID/records.json`, `calls.jsonl`, `evaluations.json`에 있다. `comparison.csv`, `report.md`, `summary.json`, `usage.json`, 사람 판정도 함께 저장한다. `calls.jsonl`은 setup/rag/evaluation을 구분하며 오류·재시도도 포함한다. 모델 내부 재정렬 연산 수는 별도 counts에 기록한다. API 키나 비공개 업무 자료는 사용하지 않는다. PDF에는 원래 공개된 기관 담당자 정보가 포함될 수 있다.

재개/백업은 원문과 설정이 같은 실행에서만 한다. 최종 ZIP을 `week-04/kwon-s-w/`에 풀고 README·노트북·실제 기록을 제출한다. 원본 저장소의 최신 제출 지침도 확인한다. 발표자료는 생성하지 않는다.
